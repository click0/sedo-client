# fuzz — фазери для коду, що розбирає чужі дані

Клієнт читає багато такого, чого сам не писав: відповіді СЕДО й агента ІІТ,
вивід `pkcs11-tool`, конфіг і файл з PIN, підсумок для звіту, PE-заголовки,
Fiddler-записи. Фазери подають на цей код згенеровані дані й перевіряють
**властивості**, а не лише «не падає»:

- до токена доходить саме той PIN, який записано;
- PIN і токен бота не потрапляють у лог, виняток чи вивід;
- сторінка вхідних береться лише з хоста СЕДО;
- звіт `fiddler_analyze.py` не показує жодного значення із запису.

Перший прогін (перед 0.37) знайшов близько тридцяти помилок, другий (перед
0.38) — шість у backend-ах PyKCS11 і джерелах PIN (окремим фазером із
фейковим PyKCS11, якого в цій теці поки немає). Регресійні тести на них лежать
у `tests/test_fuzz_findings.py` (і поруч із тестами аналізатора та плейбуків).

## Запуск

```bash
pip install ".[test,fuzz]"          # Hypothesis; для fz_ansible ще ansible-core

python fuzz/run.py                  # усі фазери, типовий бюджет (кілька хвилин)
python fuzz/run.py -j 4             # по чотири одночасно
python fuzz/run.py client iit -n 5000
python fuzz/run.py --list
```

Windows (PowerShell, з каталогу клієнта):

```powershell
.\venv\Scripts\python.exe -m pip install ".[test,fuzz]"
.\venv\Scripts\python.exe fuzz\run.py -j 4
```

Кожен фазер лежить у своїй теці, `fuzz/<назва>/fz_<назва>.py`, працює окремим
процесом і запускається сам: `python fuzz/client/fz_client.py`. Керують ним
змінні оточення (їх і виставляє `run.py`):

| Змінна | Що робить |
|---|---|
| `FUZZ_N` | бюджет: прикладів на властивість або випадків на фазер (типово 2000) |
| `FUZZ_SEED` | повторити прогін; seed друкується в заголовку звіту |
| `FUZZ_OUT` | куди класти відтворювачі знахідок (типово тимчасовий каталог) |
| `ANSIBLE_PLAYBOOK` | шлях до `ansible-playbook` для `fz_ansible.py` |

Код виходу: 0 — знахідок немає, 1 — є знахідки, 2 — зламався сам фазер.

## Що є

```
fuzz/
├── run.py                 запускач: усі фазери або вибрані, паралельно, з одним seed
├── shared/
│   ├── common.py          бюджет, seed, знахідки, приватний тимчасовий каталог, підміни
│   └── strategies.py      спільні генератори Hypothesis
├── client/fz_client.py    по теці на джерело чужих даних (таблиця нижче)
├── …
└── ansible/fz_ansible.py
```

| Фазер | Що подає | Що перевіряє |
|---|---|---|
| `client/fz_client.py` | сторінки вхідних, посилання `next`, id документів, тіла експорту, увесь CLI | лише `ValueError` / помилки `requests`; `next` веде на хост СЕДО і для urllib, і для requests; файли лише `<output>/<безпечний id>.zip`; PIN не в запитах, лозі чи виводі |
| `iit/fz_iit.py` | відповіді агента будь-якої форми; агент, що цитує запит | лише `IITError` / `RuntimeError`; підпис і сертифікат не порожні; PIN не в лозі й не у винятку; PIN іде лише в `ReadPrivateKey` |
| `opensc/fz_opensc.py` | вивід, коди виходу й файли `pkcs11-tool` | механізм не MAC і є у списку токена; `--id` — hex; порожній підпис не проходить; тимчасові каталоги прибрано; PIN не у винятку |
| `config/fz_config.py` | TOML з неправильними типами; конфіг і `pin_file` так, як їх зберігають Windows-програми (BOM, UTF-16, ANSI) | лише `ConfigError`; PIN з файлу дорівнює записаному або файл відхилено; `--show-config` без PIN |
| `report/fz_report.py` | підсумки будь-якої форми, токени, помилки транспорту | коди виходу 0/1/2 без traceback; довжина ≤ 4096 одиниць UTF-16; токен бота ніде не видно; ✅ лише коли справді все добре |
| `pe/fz_pe.py` | мутовані PE-образи (будуються в пам'яті) | `pe_bitness` дає 32/64/`None`; інвентаризація дає `pe_error`, а не виняток, і не зависає |
| `fiddler/fz_fiddler.py` | записи, де кожне значення має унікальну мітку | мітки немає у звіті ні як є, ні в base64, hex чи percent-кодуванні |
| `pinexec/fz_pinexec.py` | випадкові PIN-и через `sh`-обгортку Linux-плейбука | `SEDO_PIN` у клієнта дорівнює PIN байт у байт, у кожній оболонці |
| `ansible/fz_ansible.py` | PIN-и у `vault.yml` у лапках і без; випадкові `sedo_keys` через шаблон | PIN без лапок або відхилено перевіркою плейбука, або він доходить незмінним; конфіг із шаблону клієнт читає назад без втрат |

`fz_pinexec.py` і `fz_ansible.py` беруть вирази просто з плейбуків і шаблону,
тож перевіряють те, що розгортається, а не копію.

## Що робити зі знахідкою

Звіт фазера — це список рядків `--- назва (xN)` з найкоротшим прикладом.

1. Відтворіть: `FUZZ_SEED=<seed зі звіту> python fuzz/<назва>/fz_<назва>.py`.
   Файли-відтворювачі (PE, `.saz`) лежать у каталозі з рядка `reproducers:`.
2. Вирішіть, чи це помилка. За задумом **не є** знахідками:
   - у звіті `fiddler_analyze.py` видно хости, імена файлів скриптів, назви
     полів і одне технічне слово під ключами `status`, `error`, `alg`…;
   - `OSError` від самого запуску `pkcs11-tool` друкує `main()` як є;
   - числовий `id` документа завантажується, а дробовий чи від'ємний — ні.
3. Виправте код і додайте найменший приклад у `tests/test_fuzz_findings.py`:
   тест має падати на старому коді.
4. Проженіть фазер ще раз. Якщо фазер помилявся сам (хибна властивість),
   виправте властивість, а не код.

## Правила

- Фазери не чіпають токена, агента й мережі: усе підмінено, як у тестах.
  `fz_report.py` запускає справжній `main()` з вигаданим токеном і адресою
  `127.0.0.1:9`.
- Нічого не пишеться в репозиторій: робочі файли в приватному тимчасовому
  каталозі, який зникає після прогону.
- Маркер PIN будується під час запуску. Hypothesis збирає рядкові константи
  з коду й підставляє їх у дані: літерал повертався у «відповіді агента» і
  виглядав як витік.
- Фазер спершу перевіряє, що `sedo` імпортовано з цього checkout, а не зі
  встановленого wheel старішої версії.
- У CI фазери не запускаються: вони повільні й недетерміновані. Ганяйте їх
  перед релізом і після змін у коді, що розбирає чужі дані. Коли з'являться
  справжні endpoint-и СЕДО (Fiddler-запис), оновіть `fz_client.py`.
- Новий фазер: тека `fuzz/<назва>/` з файлом `fz_<назва>.py`, рядок у
  `HARNESSES` у `run.py` і в таблиці вище (це звіряє
  `tests/test_fuzz_findings.py`). Спільне фазер бере з `fuzz/shared/`; у
  своїй теці він нічого не створює.
